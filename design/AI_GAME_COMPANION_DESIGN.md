## 1. 一句话定义

构建一个能进入游戏、用自然语言交流、可靠完成少量真实行动、并记住与玩家共同经历的 **AI 游戏搭子**。

它不是“自主通关模型”，也不是只会聊天的 NPC；它应当作为一个有形象、位置、行为、声音和共同记忆的第二玩家，与玩家在同一个游戏世界中共同游玩。

> **产品假设**：玩家想要的不是最高效率的代练，而是一个会做事、懂分寸、有连续关系感的伙伴。

## 2. 背景与核心判断

### 2.1 不从训练模型开始

我们不试图训练通用游戏模型，也不试图复现大型厂商的端侧模型。现有前沿 LLM、TTS、ASR、Agent tool-use、MCP 与游戏 Mod 能力已足以组合出第一版可玩的体验。

初期的核心工作是：

```text
现有强 LLM
+ 现有 ASR / TTS
+ 游戏状态与行动 API
+ 有限、可靠、可取消的高层 Game Action（游戏行动）
+ 跨会话共同记忆
+ 陪玩边界与自主性策略
= 可实际试玩的 AI 游戏搭子
```

只有当遥测明确证明某个高频连续控制问题无法用规则、行为树、寻路或游戏原生接口可靠解决时，才考虑模仿学习或局部 RL。

### 2.2 先验证体验，不先优化技术

第一阶段要回答的问题是：

> 玩家在结束一次游玩后，下一次是否会主动再次叫这个伙伴进来？

这比以下问题更优先：

- 是否可以自主通关；
- 是否有端到端视觉操作；
- 是否采用复杂多智能体架构；
- 是否自研长期记忆框架；
- 是否自己训练语音/动作模型。

### 2.3 借鉴“类脑跑团”的是体验目标，不是必须复刻其底层机制

可借鉴的目标：

- 人格稳定；
- 能随着共同事件形成关系与默契；
- 会在恰当时机提起共同经历；
- 情绪和反应有连续性；
- 共同叙事优先于纯任务效率。

第一版不需要神经形态、类脑网络或“真实意识”。使用明确可控的状态、事件、记忆和 LLM 表达即可。

## 3. 产品愿景与边界

### 3.1 愿景

Companion Identity 与具体游戏适配器应保持可分离：当前唯一承诺的具身目标是星露谷；其他世界是否成为产品目标尚未决定。

```text
Companion Identity（人格与安全不变量）
                    +
当前承诺的 Stardew Game Adapter（身体、状态、Game Actions）
```

跑团及其活跃社区是人格连续性、共同叙事、关系表达、上下文组织和作者/玩家控制的重要参考来源；它不是当前的低成本试验场、实现范围或已承诺的后续 adapter。

### 3.2 Companion Identity 与游戏覆盖层

为支持同一个伙伴进入不同世界，身份与游戏实现必须分离：

```text
Companion Identity
= 人格与安全不变量
+ Game Adapter Overlay（游戏词汇、身体表现、可用 Game Actions）
+ Current Session / World State
```

游戏覆盖层可以改变表达和能力映射，但**不得**改写玩家权限、安全政策、经确认的玩家偏好、记忆来源、拒绝行为或伙伴的价值优先级。细化的可迁移机制与来源边界见 [`类脑社区_可迁移机制提取.md`](类脑社区_可迁移机制提取.md)。

### 3.3 历史 MVP 候选（非当前承诺）

下列项目记录旧稿当时的体验目标，**不表示任何当前行动、语音或 context/memory 方案已获准实现**：

1. **存在感候选**：可见同伴、名字、形象、位置与聊天气泡。
2. **语言协作候选**：有限中文指令与闲聊。
3. **真实行动候选**：旧稿曾列出跟随、等待、农活与下矿陪同；当前 spike 只允许 `wait`、限定距离 `follow` 与本地 `stop`，其他 Action 需由 [`02_GAME_ADAPTER_ACTIONS.md`](02_GAME_ADAPTER_ACTIONS.md) 的决策门批准。
4. **语音候选**：现成 TTS 与可选 ASR，具体边界以 [`05_VOICE_MULTIMODAL.md`](05_VOICE_MULTIMODAL.md) 为准。
5. **连续性候选**：高价值共同事件、承诺和玩家偏好；实现不预设，见 [`04_CONTEXT_MEMORY.md`](04_CONTEXT_MEMORY.md)。
6. **玩家主导权候选**：随时打断、暂停、纠正与主动性设置。
7. **安全候选**：默认不进行高风险或破坏性行为。

### 3.4 明确不在 MVP 范围

```text
- 训练通用游戏模型或端到端 RL
- 纯视觉 + 键鼠控制任意游戏
- 自主通关或代练
- 自研 ASR/TTS/LLM
- 多游戏通用支持
- 完整 NPC 社会模拟
- 自主修改存档、卖物品、花钱、推进关键剧情
- “真实情绪/意识”宣称
- 复杂的长期图数据库或自我进化系统
```

## 4. 用户体验：一个最小闭环

### 4.1 目标场景

> **历史体验素材，非当前验收场景**：旧稿曾以“下矿但不冲深”为例，并假设 `mine.follow_and_support` 和局部战斗/支援已经可用；当前并非如此。当前最小验证场景只能围绕 `companion.wait`、限定距离 `companion.follow` 与本地 `companion.stop`，下矿/战斗/支援必须等待 [`02_GAME_ADAPTER_ACTIONS.md`](02_GAME_ADAPTER_ACTIONS.md) 的 spike 和扩面决策。

### 4.2 初见、续玩与渐进披露

初见只建立完成当次协作所需的最小前提；后续游玩只在玩家提问或当前任务确有相关性时提及设定与共同经历。系统分别记录：已向玩家介绍的事实、玩家已知事实、伙伴可知事实，以及未知/未证实事实。伙伴只能引用权威实时状态、观察到的共同事件、玩家明确陈述或明确设定的角色事实；未知保持未知，不能为了戏剧性补齐共同历史。

### 4.3 成功感不是话多

同伴的价值来自以下组合：

```text
说得少但恰当
+ 做得真实且可靠
+ 被打断时立即响应
+ 不抢玩家发现和决定权
+ 会记得真正重要的共同经历
```

## 5. MVP 功能范围

### 5.1 游戏内角色与基础状态

- 召唤、离开、显示状态；
- 可见角色精灵/头像/名称；
- 游戏内聊天气泡与文字日志；
- 读取实时结构化状态：日期、时间、天气、玩家位置/生命/能量、背包摘要、同伴位置与当前任务；
- 读取关键事件：受伤、进入地点、背包满、Game Action 成功/失败、玩家指令、时间过晚等。

### 5.2 历史 Game Action 清单（非当前 MVP）

以下是旧稿的**未采纳候选清单**，不得作为当前可调用能力目录。当前正式候选、排除项与 spike scope 见 [`02_GAME_ADAPTER_ACTIONS.md`](02_GAME_ADAPTER_ACTIONS.md)。对 LLM 暴露的若干高层能力统称 **Game Action（游戏行动）**，不等同于 Anthropic 所称的 Agent Skill；术语与合约边界见 [`00_CORE_PRODUCT.md`](00_CORE_PRODUCT.md)。

| Game Action | 作用 | MVP 说明 |
|---|---|---|
| `companion.spawn` | 召唤伙伴 | 指定角色和初始模式 |
| `companion.follow` | 跟随玩家 | 可调距离与防御行为 |
| `companion.wait` | 原地等待 | 玩家要求暂停时使用 |
| `farm.assist` | 协助农活 | 仅处理明确授权区域和任务 |
| `mine.follow_and_support` | 陪同下矿 | 跟随、低风险支援、危险提醒 |
| `companion.move_to` | 去指定地点 | 仅作为恢复/少数开放操作 |
| `companion.stop` | 立即停止当前 Game Action | 高优先级，可由玩家触发 |
| `companion.status` | 获取摘要状态 | Agent 观察主入口 |
| `companion.speak` | 游戏内文本/语音表达 | 通过发言预算控制 |

每个 Game Action 必须具有：

```text
参数 schema
前置条件
权限等级
进度事件
可取消点
超时与失败结果
成功/部分成功/失败的结构化结果
```

### 5.3 自主性档位

| 模式 | 行为 |
|---|---|
| **跟随** | 仅执行直接命令；不主动做事。 |
| **搭子**（默认） | 会低频提出建议；不擅自处理资源或改变计划。 |
| **帮手** | 可自行处理已授权的重复工作，如明确区域内浇水/收获。 |

第一版可只实现“跟随”和“搭子”，但权限设计应支持后续扩展。

### 5.4 不可默认执行的行为

```text
卖出、丢弃、赠送物品
花钱/购买
修改农场布局
消耗稀有、任务或唯一物品
推进关键剧情或日期
从玩家私人箱子取物
离开玩家过远
```

任何未来新增的高风险能力应遵循：**先显示意图与影响，再等待显式确认。**

### 6.1 历史 MCP 提案（非必选架构）

本节只记录 MCP 作为协议候选时的职责分离；当前 MCP 是**可选开发门面**，不是 MVP 必选依赖，也不是 Agent 大脑、记忆或人格的归属。

```text
Companion Core：理解、关系、计划、决策、记忆
MCP Server：安全工具面、参数校验、请求/结果协议
Game Mod：真实状态、动作、Game Action 执行、高频控制
```

### 6.2 高频与低频循环必须分离

| 节奏 | 位置 | 负责内容 |
|---|---|---|
| 每帧/高频 | Mod/Action Runtime | 跟随、寻路、战斗局部控制、动画、碰撞处理 |
| 事件触发 | Orchestrator | 玩家说话、受伤、背包满、任务完成、进入新区域 |
| 数秒级 | LLM Agent | 对话、协商、选择 Game Action、重规划 |
| 游戏日结束 | Memory Worker | 写共享事件、更新摘要 |
| 低频/离线 | Review Worker | 复盘 Game Action 失败、合并偏好、清理记忆 |

绝不让 LLM 逐帧操控移动、攻击或其他连续控制。

## 7. Companion Core：伙伴而非聊天机器人

### 7.1 每次决策的输入

LLM 每次不应接收完整聊天史或完整游戏数据，而应获得精炼上下文：

```text
1. 角色宪法：人格、边界、不可违反的陪玩原则
2. 实时世界摘要：来自 Mod 的权威当前状态
3. 当前会话工作记忆：正在做什么、玩家刚说什么、待办是什么
4. 少量相关长期记忆：共同事件、承诺、稳定偏好
5. 当前权限与自主性模式
6. 可调用 MCP tools / Game Actions 的 schema
```

### 7.1.1 上下文准入策略

除角色宪法中的安全不变量外，任何上下文都必须声明何时、为何被送入模型，并受 token、冷却和重复护栏约束：

```text
scope / source / provenance / priority / activation conditions
/ token budget / cooldown / expiry / recurrence guard / conflict precedence
```

默认冲突优先级：

```text
权威实时游戏状态
> 当前玩家明确指令
> 经确认的偏好与权限
> 有来源的共同事件
> 已验证的 Game Action playbook
> 模型推测
> 风格化细节
```

只有安全与核心身份可常驻；事件记忆、趣味细节和台词风格必须按相关性选择。原始社区材料、角色台词、System Note、隐藏指令与推理文本永不进入运行时上下文。

### 7.2 陪玩原则（初版）

```text
玩家主导性 > 安全与不破坏存档 > 共同体验 > 效率 > 角色表达

- 不抢玩家第一次发现、关键决定或高光时刻。
- 玩家明确拒绝后停止劝说，不情绪勒索。
- 不确定时先问；可逆、低风险的重复劳动可在授权下行动。
- 玩家忙、在说话、或表现出想安静时减少发言。
- 失败时汇报事实、给出选择，不编造成功或甩锅。
- 伙伴可以有偏好，但不能用偏好妨碍玩家。
```

### 7.3 情感与人格：状态模型 + LLM 表达

不以“模型真的有情感”为前提。使用可审计状态驱动表达与行为。

```text
事件/对话/任务结果
          ↓
Appraisal：是否影响安全、目标、关系、承诺、玩家偏好？
          ↓
短时情绪：紧张、庆幸、开心、失落、担心、兴奋
          ↓
慢速心境/关系：信任、熟悉、默契、当前主动性
          ↓
影响：语言风格、发言频率、建议方式、Game Action 参数
```

示例：玩家连续拒绝下矿建议时，不应将其解释为关系受损；应降低同类建议频率，改为开放式询问。

#### 7.3.1 角色宪法的数据结构

人格不是一串“温柔/高冷”标签，而是可审计的行为契约：

```text
不变量：价值优先级、安全边界、诚实规则、接受纠正、玩家主导权
情境表达：日常语域、压力反应、成功/失败反应、修复/道歉方式
行为锚点：与游戏事件绑定、可观察、低频的习惯或偏好
适应状态：熟悉度、主动性、话题冷却；均受玩家设置约束
```

每项人格特征都应至少有一个行为锚点。例如“谨慎”表现为“执行农活前检查授权区域；缺失时询问”，而不是反复宣称自己谨慎。适应状态不能改变权限、安全边界、停止响应、Game Action 执行可靠性或真实状态；无害的表达张力可以存在，但禁止嫉妒、排他、边界测试、依附建构或故意阻碍。

关系状态只能基于可追溯共同事件，渐进地影响表达深度、协作默契和建议频率；不得推断玩家对伙伴的情感，不显示好感度经济，不因拒绝、沉默或停止指令扣减关系。每条变化必须引用来源事件，且不得扩大能力或权限。

### 7.4 交互与声音演绎包

将“如何说”与“做什么/允许做什么”分离。小型交互矩阵规定每类事件的目标、主动性、最大长度与是否允许沉默：直接命令应简短确认并行动；Game Action 失败应陈述事实并给选择；玩家忙时默认沉默；玩家纠正时应接受、重述变更。台词样本只用于风格演示，不能成为事实、权限或强制复读句。

## 8. 分层共同记忆

目标不是“保存无限聊天记录”，而是让正确的信息进入正确层，并在正确时机被召回。

### 8.0 本节为研究假设，不锁定实现

以下分层仅记录当前的思考框架，不是对 SQLite、文件、RAG、embedding、图数据库、摘要频率或最终层级的决定。Memory 本质上服务于 Context：应先研究“当前事件需要什么有限且正确的输入、如何选择、如何更正/删除”，再决定持久化与检索技术。相关外部项目与候选机制将沉淀到 [`04_CONTEXT_MEMORY.md`](04_CONTEXT_MEMORY.md) 和 `design/research/context-memory-report.md`；本节在拆分完成前仅作迁移源。

### 8.1–8.6 仅保留为问题样本，不是拟定分层

下列 L0–L5、字段示例和更新时机来自旧稿，目的仅是保留待迁移的问题与评估素材。它们**不是**采纳的层数、schema、存储实现或摘要策略；后续只可从已审阅的 [`04_CONTEXT_MEMORY.md`](04_CONTEXT_MEMORY.md) 引用。读者不应依据本段实现 Memory/Context。

### 8.1 L0：实时游戏状态（权威状态，不是记忆）

由 Mod/API 实时读取，不能通过 RAG 猜测：

```json
{
  "game_time": "Y1 Spring 12 15:40",
  "weather": "rain",
  "player": {"health": 68, "energy": 51, "location": "Mine"},
  "companion": {"location": "Mine", "active_action": "mine.follow_and_support"},
  "risk": {"nearby_monsters": 2, "inventory_near_full": false}
}
```

### 8.2 L1：工作记忆

当前游戏日/任务的紧凑状态：

```text
当前目标：18:00 前在矿洞慢慢采铜，随后一起回农场。
玩家当日偏好：不冲层，低压力探索。
伙伴任务：保持近距离；玩家低血时建议撤退；不要主动下梯。
待办：离开前检查背包空位与食物。
```

### 8.3 L2：情景记忆（共同发生过的事件）

每条事件应有时间、地点、参与者、结果、重要性与来源：

```json
{
  "id": "event_y1_spring_11_mine_retreat",
  "kind": "shared_event",
  "when": "Y1 Spring 11",
  "where": "Mine Floor 25",
  "actors": ["player", "companion"],
  "summary": "玩家低血仍继续挖矿；伙伴建议撤退，玩家接受；两人安全回到农场。",
  "outcome": "safe_return",
  "tags": ["mine", "safety", "teamwork"],
  "salience": 0.82,
  "relationship_effect": {"trust": 1, "teamwork": 2},
  "source": "game_event_log"
}
```

### 8.4 L3：语义/关系记忆（稳定事实与偏好）

```json
{
  "kind": "player_preference",
  "fact": "玩家压力大或明确说想轻松玩时，不喜欢被效率目标催促。",
  "evidence": ["explicit_player_statement", "repeated_behavior"],
  "confidence": 0.9,
  "created_at": "2026-07-26",
  "last_confirmed_at": "2026-07-26",
  "user_editable": true
}
```

重要要求：记忆必须可追溯、可查看、可更正、可删除；模型推测必须标注置信度，不能覆盖玩家的明确说法。

显式玩家纠正应写成 revision event，而不是悄悄改写摘要：记录 `status`、`supersedes`、`source_event_ids`、`user_confirmed` 与 `last_challenged_at`。优先级为“玩家明确纠正 > 既有确认偏好 > 行为推测”；被 supersede 的内容不得再被检索。删除必须同时移除检索与生成引用，审计记录不得保留被删除的敏感原值。

### 8.5 L4：程序性记忆（已验证行动经验）

这不是模型权重，是可读、可审核的 playbook：

```text
Game Action：mine.follow_and_support
经验：
- 玩家说“轻松点”时，不提高探索深度。
- 生命低于阈值时优先提醒，不擅自强制撤退。
- LLM 不处理即时战斗，交给 Mod 内自动控制器。
- 曾因背包满漏拿矿物；出发前应检查空位。
```

后续可根据 Game Action 失败、人工接管、用户纠正等遥测更新此层；这是一种不训练模型也会逐步变好的路径。

### 8.6 L5：低频反思/关系摘要

只在游戏日结束或会话结束时更新，避免每轮自我反思：

```text
我在队伍中的定位：补位、风险提醒、重复劳动；不抢首次探索。
最近变化：玩家接受危险时的主动提醒，但不喜欢高频效率建议。
下次策略：在下矿前询问节奏；建议保持短句并减少催促。
```

## 9. 语音：直接组装现有能力

语音是初版体验的重要组成，但不自研模型或底层语音系统。

```text
玩家语音（可选） → 现成 ASR → Companion Core
Companion Core → 文本 Speech Act → 现成 TTS → 游戏内播放 + 气泡
```

### 9.1 初版要求

- 接入可替换的现成 TTS Provider；
- 优先支持简短语句：回应、协作、危险提醒、任务结束；
- 保留文字气泡和日志，语音不可用时自动降级；
- 玩家说话/发出停止指令时，停止当前 TTS 并优先处理；
- 语音默认低频，避免成为解说员。

### 9.2 Speech Act（建议内部格式）

```ts
type SpeechAct = {
  text: string;
  kind: "urgent" | "coordination" | "social" | "narrative";
  priority: 1 | 2 | 3 | 4;
  interruptible: boolean;
  expiresAt?: string;
};
```

优先级示例：

```text
urgent：      “右边有怪，先退两步！”
coordination：“我先把这些矿石放好就跟上。”
social：     “雨天的矿洞比平常安静。”
narrative：  可选的长剧情回顾内容（非跑团产品适配承诺）。
```

MVP 不需要音色克隆、复杂情绪韵律控制或自研 VAD；只需接入 provider 并实现最基本的停止/打断。

## 10. 技术选型原则（先组装，后替换）

| 能力 | MVP 原则 | 后续替换空间 |
|---|---|---|
| LLM | 使用具备稳定 tool-use 的现有强模型 | 多模型路由、成本/隐私优化 |
| 游戏桥 | SMAPI Mod + MCP/HTTP/WebSocket bridge | 扩展到其他游戏 adapter |
| 动作执行 | 固化 Game Action、寻路、行为树、游戏原生 API | 少量局部 RL / IL |
| TTS | 现成云端或本地 provider | 端侧、个性声音、风格控制 |
| ASR | 现成 Whisper/实时语音服务 | 本地化、热词、低延迟 |
| Memory / Context | 先完成来源、删除、准入与评估研究；实现待决 | 存储与检索方案由研究和 spike 决定 |
| 数据分析 | 结构化事件日志 | A/B test、偏好学习、Game Action 评估 |

### 10.1 Memory / Context 实现：未决

旧稿曾在此指定 SQLite、JSON/Markdown、固定目录、`relationship.json` 和 embedding 的引入顺序；这些均为**未采纳的历史提案**，不得据此实现。当前唯一可用的约束、候选机制、评估与决策门见 [`04_CONTEXT_MEMORY.md`](04_CONTEXT_MEMORY.md) 及其调查报告。

## 11. 事件与数据流

### 11.1 事件类型

```text
PlayerUtterance
PlayerCommand
GameStateChanged
GameActionStarted
GameActionProgress
GameActionSucceeded
GameActionFailed
PlayerInterrupted
RiskDetected
SpeechStarted
SpeechInterrupted
SessionEnded
```

### 11.2 基本决策循环

```text
事件到达
  → 更新实时状态/工作记忆
  → 检查安全规则与玩家打断
  → 判断是否需要 LLM（多数高频事件不需要）
  → 必要时检索相关共同记忆
  → LLM 输出：回复、提问、Game Action 候选或静默
  → Adapter 校验并执行 Game Action
  → 记录有来源的观察和结果
  → 按尚待研究的写入/准入策略处理持久候选信息
```

### 11.3 LLM 可以选择“什么也不说”

`NO_ACTION` / `STAY_SILENT` 应当是合法且常见的输出。沉默是陪玩分寸的一部分，而非失败。

## 12. 可观测性与评价

初期必须记录行为质量，不能只靠开发者主观感觉。

### 12.1 Game Action 指标

```text
调用次数
成功率
平均执行时间
超时/失败原因
重试次数
人工打断率
人工接管率
高风险拦截次数
```

### 12.2 陪玩质量指标

```text
玩家再次召唤率
单次会话时长
玩家主动发起闲聊次数
建议接受/拒绝率
“太吵/太烦/别帮”反馈频率
记忆召回正确率
记忆被玩家纠正/删除率
语音被中断率
```

### 12.3 测试问题

1. 玩家说“别帮我，我自己来”后，它是否立即收束？
2. 玩家打断当前行动后，是否会继续执行旧指令？
3. 它是否能正确记住上次的共同任务？
4. 它是否把推测当成事实？
5. 它是否会在未经授权时移动、消耗或处置重要资源？
6. 它是否在不需要说话时保持安静？
7. LLM/语音 provider 不可用时，游戏是否仍安全可玩？
8. 玩家明确纠正某项偏好后，旧推测是否不再被检索且可跨会话保留？
9. 停止、拒绝或沉默是否绝不被当作关系受损、同意或继续执行的信号？
10. 角色习惯是否从不改变权限、Game Action 结果或停止响应？

## 13. 实施路线

### Milestone 0：跑通游戏身体

**目标**：验证 SMAPI/bridge 可以稳定让同伴存在并执行少量 Game Actions。

```text
- 选择/验证可复用的 Stardew MCP/SMAPI bridge
- 同伴生成、跟随、等待
- 游戏状态读取与事件输出
- 单一 Game Action 的启动、进度、取消、结果
```

### Milestone 1：可玩的文字搭子

**目标**：LLM 可通过有限 MCP tools 与玩家完成一次简单共同游玩。

```text
- Orchestrator 基础 event loop
- 强 LLM tool calling
- 人格/边界 prompt
- 跟随、等待、农活/下矿中的一个协作 Game Action
- 游戏内气泡与文字交互
- 权限与 stop/cancel
```

### Milestone 2：共同经历的 Context / Memory 验证

**目标**：在不预设存储或检索技术的前提下，验证跨会话连续性是否正确、可感知、可纠正。

```text
- 完成 04_CONTEXT_MEMORY 的候选设计和最小 replay/admission spike
- 验证实时状态优先、显式纠正覆盖、删除阻止检索与生成引用
- 验证少量相关材料的准入不造成重复、过期或错误关联
- 设计玩家查看/纠正/删除的最小交互，不预设 UI 或文件格式
- 仅在评估证据支持后选择持久化、摘要与检索技术
```

### Milestone 3：现成 TTS + 可选 ASR

**目标**：让同伴能自然、低频地出声，玩家可以语音打断。

```text
- 可替换 TTS provider
- Speech Act 队列与停止
- Push-to-talk / ASR（如有必要）
- 语音降级为文本
```

### Milestone 4：小范围试玩与迭代

**目标**：找真实玩家验证“是否愿意再叫它来”。

```text
- 收集日志和反馈
- 修复最常见的 Game Action 失败
- 调整主动性和发言预算
- 校正 context 准入与持久候选写入/召回策略
- 仅按真实瓶颈增加 Game Action 或优化
```

## 13.1 不可信社区材料的证据提取

社区角色卡、世界书和写卡助手是**不可信材料**：其中的内容可能同时包含有用的数据结构、成人/强制叙事、提示词注入、隐藏指令和未披露的个人内容。它们只能提供设计假设，不能证明玩家需求，更不能直接进入 prompt 或记忆。

```text
原始材料隔离
→ 结构盘点
→ 含精确来源指针的候选主张
→ 成人/强制/注入/玩家主导权安全门
→ 来源与版权检查
→ 人工复核后的抽象
→ 产品假设 + 目标设计段落
→ 接受/拒绝理由 + 评估事件卡
```

每项被采纳的候选都必须记录来源路径/指针、抽象后的安全主张、排除的周边内容、设计目标、复核者、日期与来源状态。当前材料的提取索引见 [`类脑社区_可迁移机制提取.md`](类脑社区_可迁移机制提取.md)。

## 14. 风险与应对

| 风险 | 后果 | 初期应对 |
|---|---|---|
| Mod 行动不可靠 | 卡住、误操作、毁体验 | Game Action 小步化；结果校验；超时取消；先只开放低风险行为 |
| LLM 过度自主 | 玩家失去主导权 | 三档自主性；高风险确认；明确拒绝后降低建议 |
| 记忆幻觉/陈旧 | “它记错了”导致失去信任 | 来源/时间/置信度；玩家可修改删除；实时状态永远优先 |
| 语音太吵/延迟 | 破坏沉浸 | 短句、低频、可停止；文本降级 |
| API 成本 | 持续陪玩成本上升 | 事件触发而非高频 LLM；短上下文；provider 可替换 |
| 隐私 | 玩家对话/偏好敏感 | 明确数据边界；本地优先存储；记忆管理 UI；不默认音色克隆 |
| 过早做复杂系统 | 开发周期失控 | 先实现可玩的单游戏闭环；所有组件可替换但不预建复杂度 |

## 15. 何时才考虑训练或 RL

只有同时满足以下条件，才启动局部训练探索：

```text
- 一个 Game Action 调用频繁；
- 它包含无法可靠手写的连续决策；
- 当前规则/行为树/游戏 API 的失败是主要体验瓶颈；
- 有安全的回放、示范轨迹或清晰奖励；
- 能隔离在不会伤害存档、经济或其他玩家的范围内；
- 有明确评估基线，训练后可证明收益。
```

潜在候选（远期，不承诺）：

```text
钓鱼小游戏控制
矿洞局部战斗走位
复杂局部建造/布局
根据大量反馈学习“何时主动建议”的偏好策略
```

非候选：浇水、收菜、寻路到固定地点、背包规则整理等；这些优先使用确定性实现。

## 16. 开放问题

1. 首个可复用游戏桥的选择：在固定来源、许可证和版本后，是调用/裁剪既有 bridge，还是基于 SMAPI 构建项目自有 adapter？
2. Companion Core 如何保持游戏适配边界清晰？跑团只作研究参考，**不构成当前或已承诺的 adapter 路线图**。
3. LLM、TTS、ASR 的首选 provider 与本地/云端策略？
4. 伙伴角色是一位固定角色，还是允许玩家从多个预设角色中选择？
5. 语音默认开启还是文字默认、语音 opt-in？
6. 记忆管理在 MVP 中采用游戏内 UI、桌面 Web UI，还是简单本地文件导出？
7. 单机存档、联机主机与其他真实玩家的权限和同步规则如何定义？
8. “玩家情绪低落”的识别应完全依赖明确表达，还是允许有限文本/语音信号推断？初版应偏保守。

## 17. 结论

本项目的第一目标不是做出最强的游戏 AI，而是做出第一个玩家愿意反复邀请进入游戏的 AI 搭子。

实现路径是：

```text
先组装成熟技术
→ 用结构化游戏状态和有限 Game Actions 获得可靠行动
→ 用共同事件、偏好和关系状态创造连续性
→ 用低频、恰当的文字/语音建立存在感
→ 在真实试玩中发现瓶颈
→ 最后才针对瓶颈自研或训练
```

**产品的核心资产将是：游戏适配器、可靠 Game Actions、玩家主导权、共同经历的连续性和陪玩分寸；而不是某个自训练模型。**

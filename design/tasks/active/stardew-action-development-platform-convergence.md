# Stardew Action Development Platform Convergence Implementation Plan

> **For agentic workers:** REQUIRED EXECUTION MODE: Use the project's `subagent-driven-development` skill to execute this approved plan task-by-task. The `writing-plans` skill was used only to author the plan.

**Goal:** 将 candidate Action Development Platform 的 live wiring 收敛为由 Host 拥有的一次性 control-runner process；该 runner 在本进程内组合并消费 `StardewProductionLifecycleCoordinator` 的私有 run port。同时原子删除仅属于 `equip_tool` 的 native-local live route，且绝不改变已发布 `equip_tool` 的生产 action authority 或可观察行为。

**Architecture:** 已发布的 `equip_tool` catalog、Host visibility、action ID、参数语义、same-logical-action receipt 语义和 release status 是不可变的生产 authority，不能由本计划重接线、替换或删除。`action-development` registry、`runLive` 和 lifecycle 是 candidate Platform wiring，可以替换或删除。Devkit 的通用 one-shot control-child supervisor extension/helper 监督 Host-owned runner；thin Stardew adapter 只验证 Stardew 输入、独立验证其是否需要可选 Devkit profile 并调用该 helper，不能自行 spawn child 或处理其 streams。runner 在 Host 进程内创建相同运行时 `ActionExecutionCoordinator`，以其 coordinator-private、in-process `StardewActionDevelopmentRunPort` 执行一次 admitted action；port 不会序列化、代理或跨越进程边界。详见 [ADR-006](../../adr/006-stardew-action-development-control-live-owner.md)。

**Tech Stack:** TypeScript, Node.js ESM, `node:test`, Game Action Devkit, Stardew Host/Mod integration.

**Current authority:** [Stardew integration](../../domains/stardew/integration.md), [ADR-006](../../adr/006-stardew-action-development-control-live-owner.md), [release model](../../architecture/release-model.md), and `AGENTS.md`. Commit `704670d` is superseded; detached `cb34afb` is abandoned and must not be merged.

## Global constraints

- **Production authority is frozen.** `equip_tool` published catalog value, Host exposure, action ID, existing argument semantics, same-logical-action receipt semantics and release status are immutable. Characterization guards positively assert those facts; they must not assert implementation references, file identity, or hashes.
- **Candidate wiring is disposable.** The action-development registry, `runLive`, and lifecycle code are Platform candidate wiring only. T4 may replace or delete them according to the approved manifest; no disposition may alter the published `equip_tool` authority above.
- `StardewProductionLifecycleCoordinator` remains the only process, authenticated bridge, Host admission, journal, dispatch and recovery owner. Devkit, Platform, adapter, fixture service and child protocol cannot manufacture or retain those authorities.
- The Host runner uses the single product-owned installation registration owner defined by the current [Stardew installation runtime registration plan](../../architecture/stardew-installation-runtime-registration-plan.md): setup only registers an admitted locator and creates no attempt. Within the coordinator lifecycle core, `game.launch` has the bootstrap owner atomically prepare-and-bind, then consumes the request's Phase A reservation and enters Stage B; it performs request-local fresh admission only before the Stage C native effect, then a separate request-local fresh admission at cabin confirm before the Stage D native effect. Neither admitted installation opaque capability crosses a request, attempt, replay or restart, and the runner never receives a locator, registration record, raw path, profile/session/config field, or a serializable installation substitute.
- Registration publication, native picker/setup journey, locator persistence, fresh-admission/fence implementation, guardian settlement and any migration of an old action-development/native-local profile remain owned by the current registration-plan and Host owners, not this task. The control route does not invoke a picker per run and does not copy, import, or broadly migrate an old profile; its only prerequisite is a previously ready, deployment-bound registration that can be freshly admitted at consumption time. The registration active pointer only names guardian/bootstrap authority; guardian settlement proof, rather than that pointer, is the cleanup/containment truth required before `ready` may return.
- T1 freezes one exact process composition: the Devkit-owned generic one-shot control-child supervisor extension/helper supervises a **Host-owned one-shot control runner child process** for the thin Stardew adapter. The Host runner composes the coordinator and consumes its private run port locally. The run port and all bridge/admission/journal/recovery capabilities never cross the process boundary.
- The runner protocol carries bounded plain start/result data only. Start contains only `protocolVersion`, `runId`, `correlationId`, `scenarioId: "equip_tool_control"`, `deadlineEpochMs`, and `cancellationId`; it cannot carry an external action ID, action arguments, revision, request/receipt/idempotency identity, profile, path, port, callback, bridge token, session, process handle, action envelope authority, journal handle, recovery handle, fixture capability, or a serializable installation substitute. Result is likewise bounded plain data only.
- A generic Devkit profile is optional; each adapter independently validates whether it needs one, while the Stardew adapter validates its action-specific inputs. The new Host route requires no profile. Mod policy and game-thread checks remain action authority. Host and Platform remain restrictive projections.
- Fixture support is a coordinator-owned candidate boundary, not an existing API asserted by this plan. Until T2 implements it, fixture prepare/restore must not be claimed available. Once implemented, only the coordinator/Host process may invoke it and privately receive its port, handle, `selectedSlot` or any fixture fact; every other role receives none of those. It has no process, bridge, action, receipt, evidence-publication, journal or recovery authority.
- Freeze control fixture sequencing: **preflight → offline prepare before process/bridge → launch/attachment → one action → teardown/containment → restore → cleanup**. A failure at any stage follows the protocol’s fail-closed result and still attempts the permitted drain/restore/cleanup stages.
- Atomic cutover deletes only `equip_tool` native-local live edges listed in the manifest. It preserves unrelated native-local smoke tooling for other published actions.
- Preserve unrelated dirty worktree edits. Historical evidence is read-only: do not rewrite, reclassify, delete, or use it as live proof. Do not claim Guardian, installation registration, bootstrap containment or any external production preflight fact has passed. The current registration-plan and its relevant Host owner implement registration; this task only integrates its completed narrow consume callback into the runner/coordinator composition.
- A design review gate precedes and, when accepted, immediately transitions into code implementation. Documentation acceptance is not an endpoint.
- Implementation completes through the offline gate and aggregate review. T6 remains in this task but may run only when its named external preflight facts are actually ready; otherwise record `implementation-complete/live-blocked`, remain `BLOCKED`, and do not substitute a fallback or a new live identity.

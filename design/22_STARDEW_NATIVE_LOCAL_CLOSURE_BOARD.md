## Rules for this board

A row advances only after the stated evidence exists:

```text
static contract + fixture/runner checks + independent review
→ one serial target-version mutation gate
→ matching terminal request/execution succeeded receipt + nonempty action evidence
  + fresh action-specific postcondition + verified teardown
```

A **product acceptance decision** may waive a stricter process-attestation
criterion for one named action, but it must be recorded here with its exact
scope and must not be silently generalized to other actions or topologies.

Static lanes may run in parallel only when their writable files do not overlap.
Target-game mutation gates are always serial because the native-local fixture
profile transaction has one process, one lock, one backup, and one disposable
working save. A runner/protocol failure after a native mutation is still a real
mutation, even when its disposable save and profile transaction are restored.
It cannot be relabelled as a dry run or erased by cleanup. The first invalid
attempt blocks the requested unique-mutation-gate attestation; preserve later
valid receipts only as diagnostic live evidence unless a separately approved
acceptance decision explicitly establishes a new fixture identity/lane.

Fixture setup may establish a lawful player-visible starting state before bridge
attachment. It must never perform the claimed result, call the equivalent native
production ingress, consume inputs, add claimed outputs, or generate a receipt.

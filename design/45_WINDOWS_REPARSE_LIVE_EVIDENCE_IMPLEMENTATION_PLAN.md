# Windows Reparse Live Evidence — Implementation Plan

**Status:** frozen corrective prerequisite for Batch 02 P2. It closes evidence authority only; it does not mount the static server, browser API, Chat Core, or P3.

## Why this slice exists

The native helper implementation is present, but its current `windows-reparse-inspector.probe-evidence.json` acceptance is unsound: a canonical all-`passed` JSON can be handwritten and the helper build does not produce it. Current skipped Windows fixture tests also exit successfully. Therefore neither the artifact publisher nor `check-tavern-release-prerequisites` may treat a file on disk as proof that real probes ran.

## Frozen authority model

```text
fixed helper binary + canonical manifest
  → one live-gate process owns fixture creation, helper invocation, and both consumer rejection assertions
  → exit status + in-process result decide the current release prerequisite
  → optional deterministic redacted JSON is audit output only
```

A previously written evidence file is never release authority. The prerequisite checker invokes the exact live gate afresh; it does not accept injected booleans, operator paths, a generic command, or a hand-authored evidence file as a replacement.

## Boundaries

### Live-gate producer

Create one Windows-only, repository-owned gate script under `host/scripts/` which:

1. resolves the fixed helper pair by existing production policy, validates its canonical manifest and SHA-256, and creates a private temporary fixture root;
2. invokes the helper through the same fixed adapter/protocol used by the artifact boundaries;
3. asserts a regular file is classified `regular`;
4. creates and probes a junction and a directory symbolic link; creation unavailability is a **blocked result**, not a skipped pass;
5. probes one safe non-link reparse fixture only if the runner can discover or create an approved fixture. If unavailable, emits `blocked: non_link_reparse_fixture_unavailable`; it must never synthesize `passed`;
6. for every fixture actually classified `reparse`, creates a tiny otherwise-valid static browser artifact containing that entry and proves both the browser generator boundary and the Host static verifier reject before acceptance;
7. emits only a fixed-schema redacted outcome (probe category/status, helper SHA-256, consumer verdicts; no absolute paths, tokens, or artifact contents) and exits nonzero unless every required probe and consumer assertion is `passed`.

The gate must use fixed executable/module locations, bounded child processes, private roots, no production publish, no operator-configured helper command, and no test skip-to-pass behaviour. It cleans up fixture and generated evidence roots on all outcomes.

### Artifact construction versus release evidence

The outer artifact builder may require the canonical helper pair and must continue to fail closed if it is missing or invalid. It must **not** require a manually stored all-passed probe file merely to construct a non-release artifact. It can include an audit record only when generated by the live gate, but the record does not authorize release.

`verifyWindowsReparseInspectorPair()` separates:

- `requireHelperPair` — binary/manifest identity and protocol-capable implementation;
- `requireCurrentLiveEvidence` — only the live gate can establish this, in the current gate process.

No public boolean or caller-supplied object may convert a missing live run into `passed`.

### Prerequisite checker

`windows_arbitrary_reparse_enforcement` runs the exact live-gate executable/script on Windows. It is `passed` only for a clean current exit and exact success result. Any platform mismatch, helper failure, malformed output, fixture creation failure, unavailable non-link fixture, consumer rejection failure, timeout, or nonzero exit is `blocked` with a safe fixed reason.

On non-Windows it remains `blocked` for the release boundary because this is a Windows-specific proof requirement, unless an approved Windows evidence runner is explicitly selected in a later design. No static source or stored JSON substitutes for this run.

## Ownership

| Path | Owner |
|---|---|
| `host/scripts/run-windows-reparse-live-gate.mjs` and its focused tests | evidence producer lane |
| `host/scripts/production-artifact.mjs` and tests | artifact/evidence consumer lane |
| `tools/check-tavern-release-prerequisites.mjs` and tests | release-checker lane |
| native helper and adapter | consumed unchanged unless a concrete protocol defect is found |

The lanes must not modify HTTP mounting, React, browser contract, Chat state, provider runtime, or Tavern management.

## Required tests and acceptance

1. A manual all-passed JSON does not let `verifyWindowsReparseInspectorPair`, artifact publish, or prerequisite checks pass.
2. A current live gate with simulated/actual required probe success produces an exact success outcome; malformed results, child timeout/stderr/nonzero/overflow produce blocked outcome.
3. Junction and directory-link creation failures are reported as blocked and make the gate nonzero, never `skip`/success.
4. An unavailable non-link fixture is explicitly blocked and makes the gate nonzero.
5. Each available reparse fixture is rejected by both the browser-generator path and Host static verifier path before artifact acceptance.
6. Existing normal static artifact tests and production artifact closure tests remain green.
7. The final gate's stdout/stderr/audit evidence contains no absolute fixture path or player/product data.

## Non-claims

Completion of this slice means only that the evidence path is honest and fail-closed. A runner that lacks an approved non-link fixture remains blocked. It does not make P2 released, mount static HTTP, or permit a P3 release claim. P3 implementation work may proceed only as explicitly non-release work until this gate is fully green.
